좋습니다. 지금은 **리팩토링보다 “기능적으로 하나의 Persistent Job Agent가 완결되는 지점”까지 가는 것**을 우선으로 두는 게 맞습니다.

제가 제안하는 전체 Plan은 다음 순서입니다.

## 전체 방향

```text
Phase 0. 현재 상태 안정화
Phase 1. M1 Curator 완결
Phase 2. RQ Answer Report 완결
Phase 3. 지식 갱신 → Report 갱신 루프
Phase 4. 외부 자문 직무 완결
Phase 5. 연구 논문 작성 직무 완결
Phase 6. Workspace portability / merge 완결
Phase 7. End-to-End 직무 시나리오 검증
Phase 8. 그 다음 리팩토링
```

핵심은 **각 Phase가 하나의 실제 사용 시나리오로 끝나야 한다**는 것입니다.

---

# Phase 0. 현재 상태 안정화

지금까지 구현한 기능을 새로 확장하기 전에 한 번 고정합니다.

대상은:

- Research Question lifecycle
- Literature discovery
- Paper review
- Knowledge Card
- Ontology
- Attention
- Knowledge UI
- Portable Workspace

여기서는 새로운 기능을 만들기보다는 **현재 깨지는 부분만 수정**합니다.

완료 기준은 간단합니다.

> 앱을 새로 시작해서 RQ 하나를 만들고, Knowledge Card와 Ontology까지 중단 없이 한 번 수행 가능

여기까지를 M1의 baseline으로 봅니다.

# Phase 1. M1 Curator 완결

현재 거의 도달했습니다.

M1의 완결된 직무는 다음입니다.

```text
Research Question

Initial Literature Search

Paper Discovery

Paper Review

Knowledge Card Proposal

Researcher Approval

Knowledge Card

Ontology Update
```

여기에 **추가 문헌조사**까지 포함해야 합니다.

```text
RQ
 ├─ Initial Literature Round
 ├─ Additional Literature Round #1
 ├─ Additional Literature Round #2
 └─ ...
```

각 Round에서:

```text
Intent
→ Papers
→ Paper Review
→ Knowledge Cards
→ Approval
```

이력이 RQ 아래에 남아야 합니다.

### Phase 1에서 확인할 핵심

Research 화면에서 예를 들어:

```text
RQ-001
상태: 추가 문헌조사

Initial Round
  Paper 12
  Approved KC 6

Additional Round #1
  Paper 8
  Approved KC 3

Knowledge
  KC 9

Ontology
  Type 7
  Relation 10
```

처럼 **질문의 연구 과정 전체가 보이는 상태**가 좋습니다.

### 완료 기준

다음 두 시나리오가 모두 가능해야 합니다.

**Scenario 1**
> 새로운 연구질문 → 문헌조사 → 논문 읽기 → Knowledge Card 승인

**Scenario 2**
> 기존 연구질문 → 추가 문헌조사 → 새로운 Knowledge Card 승인

# Phase 2. M2 — Research Question Answer Report

이게 다음 구현의 핵심입니다.

M1이 만든 지식을 M2가 처음으로 **산출물**로 바꾸는 단계입니다.

입력:

```text
Research Question
+
Approved Knowledge Cards
+
RQ-specific Paper Evidence
+
Ontology
+
Research Context
```

출력:

```text
RQ Answer Report
```

초기에는 1~3페이지 수준이 적당합니다.

Report 구조는 예를 들면:

```text
Research Question

Executive Answer

What We Know
- 주요 Knowledge Card 기반 주장

Evidence
- Papers
- source evidence

Interpretation
- 연구위원의 종합 판단

Limitations / Uncertainty

Open Questions

Recommended Next Research
```

여기서 중요한 것은 **Report가 그냥 LLM output이 아니라 durable object**가 되는 것입니다.

```text
Report
- report_id
- rq_id
- version
- status
- source_knowledge_card_ids
- source_paper_ids
- ontology_version
- draft
- researcher_comment
- created_at
```

### Human flow

```text
M2 drafts
   ↓
Attention: Review
   ↓
Researcher 수정/검토
   ↓
Attention: Decision
   ↓
Approved Report
```

### 완료 기준

**Scenario 3**
> 현재 승인된 지식을 바탕으로 RQ Answer Report 초안 생성 → 검토 → 승인

# Phase 3. Knowledge Update → Report Update Loop

이 단계가 Persistent Job Agent로서 굉장히 중요합니다.

보고서를 한 번 만들고 끝나는 것이 아니라:

```text
Knowledge changes
  
Report becomes stale
  
M2 detects impact
  
Update proposal
  
Researcher approval
  
Report v2
```

가 되어야 합니다.

예를 들어:

```text
RQ-001

Report v1
  KC-001
  KC-002
  KC-003

새 문헌 조사
   ↓
KC-004 approved

Report 상태
  "새로운 지식이 추가되었습니다"
```

Attention:

```text
[Decision · Research]

새로운 Knowledge Card가
RQ-001의 기존 답변에 영향을 줄 수 있습니다.

영향 카드
- KC-004

[보고서 갱신]
[추가 탐색]
[현재 보고서 유지]
```

그리고:

```text
Report v1

Report v2
```

로 versioning합니다.

Ontology 변경도 같은 trigger가 될 수 있습니다.

```text
KC update
Ontology update
Additional literature
Researcher context update
```

### 완료 기준

> 새로운 KC 승인 → 기존 Report stale 표시 → M2 재작성 → Report v2 승인

이 단계가 되면 **지식 축적 → 판단 → 산출물 갱신** 루프가 완성됩니다.

# Phase 4. External Advisory 직무 완결

그 다음 외부 자문입니다.

외부 요청은 Research Question과 성격이 조금 다릅니다.

```text
External Advisory Request
    
M2 interprets request
    
Knowledge search
    
Evidence sufficiency judgment
```

여기서 두 갈래입니다.

### 충분한 경우

```text
Internal Knowledge
 
Advisory Answer Draft
 
Researcher Review
 
External Answer
```

### 부족한 경우

```text
Knowledge Gap
 
New Research Question
or
Additional Literature Intent
 
M1 Curator
 
Knowledge Updated
 
M2 Answer
```

이 흐름이 중요합니다.

외부 질문에 그냥 LLM이 답하는 것이 아니라:

> **현재 연구위원의 축적된 지식으로 답할 수 있는가?**

를 먼저 판단하게 됩니다.

그리고 외부 자문 과정에서 얻은 새로운 내용은 내부 지식 후보가 될 수 있습니다.

```text
Advisory interaction
  
Potential Knowledge
  
Researcher approval
  
Knowledge Card
```

### 완료 기준

두 시나리오 모두 필요합니다.

- 충분한 지식 → 바로 자문 답변
- 부족한 지식 → M1 탐색 → 지식 갱신 → 자문 답변

# Phase 5. Research Paper Writing

그 다음에 이전 구현에서 만들어둔 paper/coauthor 기능을 다시 살펴보는 게 좋습니다.

여기서 기존 코드가 실제로 필요한지 판단할 수 있습니다.

Paper는 Report보다 상위 산출물로 봅니다.

```text
Research Questions
+
Approved Reports
+
Knowledge Cards
+
Papers / Evidence
+
Ontology
  
Research Paper
```

처음에는 두 종류를 명확히 분리하면 좋습니다.

### Short Paper

약 2페이지.

목적:

- 아이디어 정리
- workshop / magazine pitch
- 내부 연구 초안

구조:

```text
Problem
Core Argument
Evidence
Implications
Limitations
```

### Full Paper

약 8~10페이지.

```text
Introduction
Related Work
Method / Approach
Case
Results / Findings
Discussion
Lessons Learned
Conclusion
```

여기서 M2는 논문 전체를 한 번에 생성하는 것이 아니라:

```text
Paper Plan
   ↓
Section Draft
   ↓
Researcher Review
   ↓
Revision
   ↓
Integrated Draft
```

식으로 가는 것이 좋습니다.

### Citation grounding

논문의 문장은:

```text
Claim
→ Knowledge Card
→ Paper
```

로 traceable해야 합니다.

이게 현재 만든 Knowledge Card와 Evidence Library의 가치를 가장 잘 살립니다.

### 완료 기준

- 2-page paper 생성
- section 단위 수정
- full paper 확장
- reference/evidence traceability 확인

# Phase 6. Workspace Portability / Merge

이 단계에서는 최근 만든 저장 구조를 실제 완결합니다.

목표:

```text
workspace.json
pdf/
```

만 있으면 어디서든 복원 가능.

SQLite는:

```text
optional derived cache
```

입니다.

기능은:

### 6-1 Export

```text
DB
 ↓
workspace.json
pdf/
```

### 6-2 Restore

```text
workspace.json
pdf/
 ↓
DB rebuild
```

### 6-3 Consistency

```text
DB ↔ JSON ↔ PDF
```

비교.

### 6-4 Merge

집:

```text
workspace A
```

학교:

```text
workspace B
```

를 가져와서:

```text
Merge Preview

Only A
Only B
Same
Changed
Conflict
Possible Duplicate
```

로 보여줍니다.

그리고 merge 후:

```text
workspace C
```

를 생성합니다.

이때는 기존 server/local sync를 제거할 수 있습니다.

# Phase 7. End-to-End Job Scenarios

기능을 모두 구현한 뒤 **코드가 아니라 직무 시나리오로 검증**합니다.

제가 생각하는 최종 테스트 세트는 8개 정도면 충분합니다.

1. **새 RQ → Knowledge**
2. **RQ → 추가 문헌조사 → Knowledge 갱신**
3. **Knowledge → Ontology**
4. **RQ → Answer Report**
5. **새 지식 → Report Update**
6. **External Advisory → Answer**
7. **Knowledge 부족 Advisory → M1 조사 → Answer**
8. **RQ/Reports → Research Paper**

그리고 별도로 운영 시나리오:

9. Workspace export/restore
10. Home/School workspace merge

이 10개가 모두 돌아가면 에이전트의 전체 직무 경계가 상당히 명확해집니다.

## 전체를 크게 보면

현재 프로젝트는 사실 세 단계로 나뉩니다.

```text
M1 Curator
Knowledge Production
─────────────────────
Research
Literature
Paper
Knowledge Card
Ontology


M2 Advisor
Knowledge Utilization
─────────────────────
RQ Answer
Report
Advisory
Research Direction
Paper Writing


Persistent Job Infrastructure
─────────────────────
Attention
Memory
Workspace
Versioning
Merge
Continuous Update
```

현재 위치는 **M1 거의 완결 → M2 진입 직전**입니다.

따라서 실제 다음 개발 순서는 저는 이렇게 잡겠습니다.

**Phase 1 M1 잔여 정리 → Phase 2 RQ Answer Report → Phase 3 Report Update Loop → Phase 4 Advisory → Phase 5 Paper Writing → Phase 6 Workspace Merge → End-to-End 검증 → Refactoring**

이 순서라면 기존에 구현해둔 M2/Report/Paper 관련 코드도 실제로 다시 평가하면서 살릴 수 있습니다.
